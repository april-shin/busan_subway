# 열차 시간표 (하이브리드: 역별 시간표 + 배차간격 폴백)

`assets/json/line_schedules.json`에 23개 노선의 양방향 운행 스케줄을 컴팩트 JSON으로 보유한다:
- 노선별 상행(내선)/하행(외선) 첫차·막차 시간
- 시간대별 배차간격 (첨두 06:30-09:00/16:30-19:30, 비첨두, 심야)
- 하행 전용 배차간격이 상행과 다를 경우 `pD` 키로 별도 저장
- 역별 정확한 출발시각 목록이 있으면 `t` 키로 저장 (배차간격 대신 사용)

## 컴팩트 JSON 스키마

```json
{
  "id": "1",
  "wd": {
    "f": ["05:20","05:18"],
    "l": ["00:48","00:42"],
    "p": [["05:00","06:00",5],["06:00","09:00",4]],
    "t": {
      "P01": [null, [330, 340, 350, 360]],
      "P05": [[335, 345, 355], [328, 338, 348]]
    }
  },
  "we": { ... }
}
```
- `id` = lineId, `wd` = 평일 (필수), `we` = 주말 (옵셔널, 없으면 `wd`와 동일)
- `f` = firstTrains [상행/내선, 하행/외선], `l` = lastTrains [상행/내선, 하행/외선]
- `p` = 공유 배차간격 [[시작,종료,배차분]], `pD` = 하행 전용 배차간격 (상이할 경우만)
- `t` = 완행 역별 시간표 (옵셔널). `stationId → [상행출발분목록, 하행출발분목록]`
  - 각 목록은 자정 기준 분(minute) 단위 정렬된 정수 배열 (예: 330 = 05:30)
  - 자정 이후 출발은 1440+ (예: 24:49 → 1489)
  - ⚠ **노선에 따라 0~1439 로 담기도 한다** — 경의중앙이 그렇다(00:39 → 39).
    앱은 `departure_candidates.dart` 의 `lateNightCutoffMinutes`(240)로 두 인코딩을
    모두 흡수한다. 이 예외를 모른 채 "자정 넘김은 항상 1440+"로 가정하면 오진한다
    (실제로 2026-09-12 에 그렇게 한 번 틀렸다 — 아래 경의중앙 항목의 '오진 기록').
  - `null`은 해당 방향 출발 없음 (종착역 등)
  - `t`가 없는 역은 `p` 배차간격으로 폴백
- `tE` = 급행 역별 시간표 (옵셔널, 구조는 `t`와 동일). 급행 미정차역은 키가 없다.
  - 급행이 역을 통과하는 노선(9호선)에서 완행(`t`)과 분리 저장한다. 한 배열로 합치면
    급행 미정차역에 급행 출발시각이 섞이는 오류가 생기기 때문.
  - 급행 모드(`{base}E` 가상 노선) 라우팅 시 `findNextDeparture(express: true)`가 `tE`만 조회하며,
    해당 역 급행 데이터가 없으면 완행과 섞지 않고 배차간격으로 폴백한다.
  - 파싱: `DaySchedule.expressStationDepartures` (완행은 `stationDepartures`)
- 상하행 첫차/막차가 동일하고 `pD`/`t`/`tE` 없으면 하행 데이터는 상행으로 자동 폴백

## 역별 시간표 지원 노선

- **김포골드라인 (P01~P10)**: 구간운행(short-turn)이 있어 역별 배차간격이 다름. 10개 역 전체 평일/주말 시간표 포함.
  (수집 경로는 아래 "비서울교통공사 노선 12개" 항목과 동일 — 여기는 노선 고유 특성만 정리.)
  - 데이터 출처: **getTrainSch 단일화**(2026-07-27). 이전에는 P01~P09 가 korailinfo.com 수동 데이터,
    P10 은 미수집이었다. korailinfo 원본이 구간운행 편성을 상당수 누락해(구래 김포공항방면 127편 →
    실제 258편) 구래 출발 조회 시 실제보다 늦은 열차를 안내하던 문제가 있었다. 이관으로 평일 총
    출발이 3,773 → 4,343건이 됐다.
  - 편성 체계(평일, 수집 시 확인): **3xxx** 전구간(양촌↔김포공항) 100편, **2xxx** 구간운행
    (구래↔김포공항) 158편, **7xxx** 비영업 2편(제외 — 아래 참고).
  - 방향별 편수가 구래에서 꺾이는 것이 정상이다 — 158편이 구래에서 회차하므로:
    - 김포공항 방면: 양촌 100 → **구래 258** → 마산~고촌 258~259
    - 양촌 방면: 김포공항~마산 259 → **구래 101** → 양촌 0(종점)
  - 종점 처리: P01(양촌)은 `[null, 공항방면]`, P10(김포공항)은 `[양촌방면, null]`.
  - **`f`/`l` 도 `t` 에서 도출한다**(2026-09-12). `build_gettrainsch_timetable.dart` 의
    `_deriveRepresentative` 가 담당하며 규칙은 경의중앙과 같다(방향별 정상 시간대
    최소 → `f`, 운영일 기준 최대 → `l`, `p` 첫 band 시작을 이른 쪽 `f` 에 맞춤,
    꼬리 갭은 유지). 그 전에는 `extract_schedules` 의 하드코딩 추정치라 실측과
    어긋나 있었다 — 평일 `l=23:30` vs 실측 막차 24:58, 주말 `f=06:00` vs 실측 05:26.
    - 값: 평일 `f=['05:30','05:26']` `l=['00:58','00:51']`,
      주말 `f=['05:30','05:26']` `l=['23:57','23:52']`.
      `p[0]` 시작은 평일 05:30→05:26, 주말 06:00→05:26.
    - 영향 실측(평일·토·일 각 10역 × 2방향 × 1440분 = 86,400 조합. ⚠ 이런 스윕의
      건수는 **요일 표본에 따라 달라진다** — 월요일 00:00~00:29 는 전날이 주말이라
      전날-운영일 분기가 다르게 풀린다. 질적 결론(`t` 없는 방향에만 갇힘)은 불변): 답이 달라진 것은
      `t` 가 없는 종점 방향 2개(P01 상행·P10 하행)의 6,006건뿐이고 "운행 종료"로
      바뀐 조합은 0건이다. 그 방향엔 애초에 출발 열차가 없다.
    - `extract_schedules.dart` 의 `_representativeCarryOverLines` 에 김포골드가 들어
      있어 그 도구를 다시 돌려도 추정치로 되돌아가지 않는다.
  - `tool/convert_gimpo_timetable.dart` / `build_gimpo_json.dart` 는 **레거시**(korailinfo 경로). 더 이상
    실행하지 말 것 — 실행하면 P01~P09 가 구간운행 누락 데이터로 되돌아간다.
- **경의중앙선 (K01~K57)**: 급행/완행 혼합 운행으로 역별 정차 패턴이 다름. 57개 역 전체 평일/주말 시간표 포함.
  - 경의중앙선(용문↔문산) + 경의선(서울↔문산) 열차를 역별로 통합
  - K54(서울역)·K57(신촌, 경의선)은 K20(가좌)에서 분기하는 지선, 경의선 열차만 정차
    (K57 은 엑셀의 '신촌' 행 — `build_center_line_timetable.py` 의 ABBREV 로 매핑)
  - K55(임진강), K56(운천)은 K01(문산) 이북 연장 구간, 하루 2~4편 운행
  - 데이터 출처: 코레일 "열차운임/시간표" 게시판의 전동열차 시각표 엑셀
    (`assets/excel/center_line_wd260901.xlsx` 평일 · `center_line_we260901.xlsx` 휴일,
    2026-09-01 시행분). 재생성은 `tool/build_center_line_timetable.py`.
  - ⚠ **2026-09-01 시행분부터 워크북 구조가 바뀌었다.** 이전
    (`center_line260228.xlsx`, 2026-02-28 시행)은 평일·휴일이 한 파일에 8시트
    (`경의중앙선 상행(평일)` 식)였는데, 지금은 평일/휴일이 파일로 갈리고 시트명에
    요일이 없으며 경춘선·서해선·ITX청춘·망우직결선 시트가 같은 파일에 들어 있다.
    도구는 신 구조만 읽는다(구 파일은 대조용으로 남겨 둠).
  - **시트 → `t` 인덱스 매핑은 코레일 라벨과 다르다.** 앱 인덱스는 "역ID 감소=0,
    증가=1"이라 노선별로 뒤집힌다: 경의중앙선 상행(→문산)=0 · 하행(→지평)=1 ·
    경의선 상행(→서울역)=**1** · 경의선 하행(→문산)=**0**. 두 계통이 겹치는
    문산~가좌 구간은 역 단위로 합친다.
  - 엑셀은 역마다 두 행(역명 행=도착, 다음 빈 이름 행=출발)이고 우리가 담는 값은
    **출발**이다. 분 변환은 **반올림(half-up)** — 초는 :00/:30 뿐이라 내림을 쓰면
    기존 데이터와 1분씩 어긋난다. 종착역은 도착만 있어 자연히 제외된다.
  - 앱에 없는 역(`도라산`)과 구 엑셀의 `연계열번` 행은 버린다.
    경의선 `신촌` 은 **2026-10-16 K57 추가 이후 `ABBREV` 로 `신촌(경의중앙선)`
    에 매핑한다** — `IGNORED` 로 되돌리지 말 것(되돌리면 K57 시간표가 사라진다).
  - **`f`/`l`(노선 첫차·막차)도 같은 도구가 `t` 에서 도출한다**(2026-09-12).
    방향별로 "정상 시간대(240~1439분) 최소"를 `f`, "운영일 기준 최대"를 `l` 로
    쓴다. 이전에는 `extract_schedules.dart` 의 하드코딩 추정치(평일
    05:10~23:40)여서 실측(05:00~00:39)과 어긋나 있었다.
    - 값: 평일 `f=['05:00','05:00']` `l=['00:39','00:27']`,
      휴일 `f=['05:04','05:21']` `l=['00:38','00:25']`.
    - **`p` 의 첫 band 시작도 도출된 첫차에 맞춘다**(평일 05:10→05:00,
      휴일 05:30→05:04). `f` 만 당기고 band 를 두면 그 사이를 덮는 band 가
      없어 `_findNextByHeadway` → `_findPeriod` 가 null("운행 종료")을 돌려준다
      (정렬 전 실측: 평일 30건 + 토·일 **각각** 44건 = 118건).
      band 의 **시작만** 옮기고 간격·끝은
      두는데, 끝을 `l` 까지 늘리면 실재하지 않는 심야 출발을 지어내기 때문이다.
      `p` 는 방향 공용이라 두 방향 `f` 중 이른 쪽에 맞춘다.
    - ⛔ **꼬리 갭(마지막 band 끝 ~ `l`)은 의도적으로 남긴다.** 평일 23:40~00:39
      는 여전히 배차간격 경로에서 null 이다. 머리 갭은 "이미 있는 첫차를 못
      찾는" 문제라 메우고, 꼬리 갭은 끝을 늘리면 "없는 심야 열차를 20분마다
      지어내는" 문제가 되므로 두는 것이다 — 같은 논리로 끝을 늘리지 말 것.
    - 소비자 영향은 거의 없다 — 실측(평일·토·일 각 56역 × 2방향 × 1440분 =
      483,840 조합 전수 대조)에서 답이 달라진 것은 `t` 가 없는 종점 방향 3개
      (K53 하행·K54 하행·K55 상행)뿐이고(평일 1,230건, 토·일 각 4,137건),
      "운행 종료"로 바뀐 조합은 **0건**이다. 그 방향엔 애초에 출발 열차가 없다.
      고친 이유는 값 자체의 정확성이다 — 첫차·막차를 화면에 쓰는 기능이 생기면
      즉시 오답이 된다(2026-08-13 앵커역 정정과 같은 사유).
    - ⚠ **오진 기록**: 이 작업을 시작할 때 "`f`=05:10 이라 05:00~05:09 조회가
      전날 운영일로 폴백한다"고 진단했으나 **틀렸다.** 전날 분기는
      `prevDepartures.last >= 1440` 을 요구하는데 경의중앙은 자정 넘김을
      0~239 로 담아(정확히 1440 인 wd K16 상행·K38 하행도 `cur+1440` 초과가
      될 수 없어 매칭 불가) 그 분기를 타지 않는다. 이 인코딩은
      `departure_candidates.dart` 와 `line_schedule_anchor_sanity_test.dart` 에
      **이미 적혀 있던 사실**이다 — 같은 추론을 처음부터 다시 밟지 말 것.
    - **`p` 의 간격값·`pD` 는 여전히 추정치다.** 경의중앙은 57역 전부 `t` 를
      보유해 배차간격 경로가 위 3개 종점 방향에서만 도달 가능하고, 그 방향엔
      출발 열차가 없다. 도출 대상에서 뺀 이유다. 바꾸려면 JSON 직접 패치뿐이다
      (`extract_schedules.dart` 의 추정치를 고쳐도 carry-over 가 덮어쓴다).
    - ⚠ `extract_schedules.dart` 를 다시 돌려도 도출값이 유지되도록 그쪽에
      `_representativeCarryOverLines`(경의중앙·김포골드·우이신설·인천1 의
      `f`/`l`/`p`/`pD` 를 기존 파일에서 물려받음)를 두었다. 회귀 가드:
      `test/data/derived_first_last_test.dart`
      (노선당 11 케이스 × 4 노선 = 44 — 도출 규칙 8 + 첫 band 정렬 2 + 추정치 복귀 1).

## 노선 대표값 (`f`/`l`/`p`/`pD`) — 앵커역 규칙

역별 시간표(`t`/`tE`)와 **출처가 다른 별개 계층**이다. `tool/extract_schedules.dart` 가
노선마다 **역 하나(앵커역)** 의 getTrainSch 행에서 첫차·막차·배차간격을 계산한다.

**앵커역은 반드시 "양방향 전구간 운행역"으로 고른다.** 회차역을 쓰면 그 방향 열차
대부분이 당역종착이라 API 가 `trainDptreTm=null` 을 주고, 살아남은 소수 편성이 노선
전체 대표값이 된다. 2026-08-13 에 두 노선을 정정했다:

| 노선 | 구 앵커(회차역) | 결손 | 신 앵커 |
|---|---|---|---|
| 수인분당 | 왕십리 | 상행 168행 중 159편 당역종착 → 9편 | **서울숲** |
| 경춘 | 상봉 | 상행 56행 중 42편 당역종착 → 14편 | **망우** |

정정 전 값과 정정 후 값:

| 노선·요일·방향 | 정정 전 `f` ~ `l` | 정정 후 |
|---|---|---|
| 수인분당 평일 상행 | 07:32 ~ 18:51 (배차 band 1개) | 05:51 ~ 00:18 (8개) |
| 수인분당 주말 상행 | 11:02 ~ 16:59 (1개) | 05:51 ~ 00:24 (8개) |

    이라 23:00 이후엔 `lastTrainMinutes` 가 커져도 여전히 null(꼬리 갭 정책).
  - ⚠ **우이신설 주말에서 `값 → null` 4건이 나왔다** — W01 상행·W13 하행(양 종점의
    진행 불가 방향)의 23:58~23:59 가 "00:00 출발"에서 "운행 종료"로 바뀌었다.
    `l` 이 추정치 00:00 에서 실측 23:58 로 **앞당겨진** 결과이고, 그 방향의 마지막
    출발이 실제로 23:58 이므로 의도된 정정이다. 옛 00:00 은 실측이 아니라
    `_nextInPeriod` 의 마지막 분기가 만든 값이었다 — 23:58 에서 5분 그리드의 다음
    칸이 1440 이 되어 band 끝(`"00:00"` → 1440)을 넘고, `min(band 끝, l)` 이 다시
    1440 이라 "00:00 출발"이 나왔다. **편성이 0편인 방향에서 유령 출발 하나를
    2분 창에서 지운 것**이다. 다른 세 노선의 전환에서는 `값 → null` 이 0건이었다.
    - 이로써 우이신설 주말은 `p.last.end`(1440) > `l`(1438) **역전** 상태가 됐다.
      꼬리 갭 정책상 의도된 것이지만 데이터 형태 검사로는 잡히지 않으므로,
      `derived_first_last_test.dart` 의 "꼬리 갭" 그룹이 **동작으로** 잠근다
      (W01 상행·W13 하행 23:58~23:59 = null, 23:57 = 23:58). 평일도 꼬리 갭이
      0 → 18분(`p` 끝 00:40 vs `l` 00:58)으로 넓어졌다.
  - `p[0]` 정렬의 **문자열 비교 함정도 이번에 없앴다(Dart·Python 양쪽).** 우이신설
    주말 `p` 는 단일 band `['05:30','00:00',5]` 라 끝이 자정 넘김 벽시계인데,
    예전 코드는 `"05:31" >= "00:00"` 을 참으로 읽어 정렬을 거짓으로 건너뛸 수
    있었다. 지금은 `bandEndMinutes` 로 분 단위 비교한다 — **`TimePeriod.endMinutes`
    를 그대로 미러**한다(`"00:00"` → 1440, 그 외 끝이 시작보다 **작을 때만** +1440).
    ⚠ `DaySchedule.lastTrainMinutes` 의 `<=` 규칙과 혼동하지 말 것. 그쪽은 길이 0
    (`start == end`) band 를 하루짜리로 읽지만 `endMinutes` 는 보정하지 않는다.
    실데이터에 `['00:00','00:00',N]` 길이 0 band 가 있다(1~9호선·SB·인천2) — 다만
    끝이 `"00:00"` 이라 두 규칙 모두 1440 을 내므로 현재 결과 차이는 없다.
  - 공통 모듈 계약(자정 넘김 두 인코딩·band 끝 규칙·값 없을 때 실패 처리)은
    `test/tool/derive_representative_test.dart` 17 케이스가 잠근다.
  - 회귀 가드: `test/data/derived_first_last_test.dart`(도출 대상 노선 목록 기반).

### `f` 와 `p[0].start` 사이 구멍 (2026-09-12 보정)

3번 경로(`_findNextByHeadway`)에는 **첫차(`f`)는 지났는데 첫 배차 band 는 아직
시작하지 않은 구간**이 있었다. `currentMinutes < firstMin` 분기(첫차 반환)를 이미
지났고 `_findPeriod` 는 덮는 band 가 없어 빈손이라, 함수 전체가 `null` 을 돌려
상위가 **"운행 종료"로 오판**했다 — 첫차 직후인데도.

`_findNextByHeadway` 가 `_nextInPeriod` 의 `null` 을 받으면 `_findNextPeriod` 로
**다음 band 시작**을 돌려주도록 보정했다. `currentMinutes >= lastTrainMinutes`
판정은 그 앞에 있으므로 막차 이후 `null` 은 그대로다. 급행은 애초에
`_findNextByHeadway` 진입 전에 차단되므로(배차간격 폴백 금지 정책) 영향 없다.

- 해당 데이터(`f` < `p[0].start`): **경춘 주말 하행**(05:32 vs 06:00),
  **경강 평일·주말 상행**(05:30 vs 06:00). 둘 다 `extract_schedules.dart` 의
  앵커 분석 산출값이라 그 도구를 다시 돌리면 재현되므로, 데이터가 아니라
  **코드에서 막는 것이 유일하게 지속되는 방어**다.
  (경의중앙·김포골드는 도출 도구가 `p[0].start` 를 `f` 에 맞춰 애초에 구멍이
   없다. 그 정렬은 남겨 두되, 이제 이 보정이 일반 방어선이다.)
- 영향 실측(전 24개 노선 791역 × 2방향 × 1440분 × 평일·주말 = **4,556,160
  조합** 전수 대조): 차이 **88건이 전부 `null` → 값**이고 반대 방향 전이는
  0건이다. 내역은 경춘 C24 하행 28건(주말 05:32~05:59), 경강 GG01 상행
  60건(평일·주말 각 05:30~05:59)뿐 — 두 노선 모두 전 역이 `t` 를 가져 이
  폴백은 **양 종점의 진행 불가 방향**에서만 도달한다.
- 회귀 가드: `test/domain/usecases/find_next_departure_test.dart` 의
  "첫차와 첫 배차 band 사이 (구간 결함 회귀)" 그룹.
- band **사이** 공백은 현재 데이터에 없다(전 노선·요일 실측 0건). 보정은 그
  경우에도 다음 band 시작을 주지만, 그런 공백이 생기면 데이터 쪽을 의심할 것.
  (`_nextInPeriod` 가 그리드를 band 끝 너머로 넘길 때 이미 쓰는 의미론과 같다.
   좁히면 "그리드로 진입하면 건너뛰고, 공백 한복판에서 조회하면 운행 종료"라는
   두 답이 생긴다.)
- ⛔ **대칭 케이스(`l` > 마지막 band 끝)는 닫지 않았다.** 같은 분기로 들어오지만
  `_findNextPeriod` 도 빈손이라 **여전히 null** 이 나간다. 실데이터: 경의중앙
  (band 끝 23:40 vs `l` 00:39), 김포골드(23:30 vs 00:58), 경강 주말 하행.
  머리 갭은 "이미 있는 첫차를 못 찾는" 문제라 메우고, 꼬리 갭은 메우면 "없는
  심야 열차를 배차간격으로 지어내는" 문제가 되므로 **의도적으로 둔다**(위
  경의중앙 항목의 '꼬리 갭'과 같은 판단). 현재 동작을 고정한 테스트가
  같은 그룹에 있다 — 닫게 되면 그 테스트가 먼저 깨진다.
- 이 두 경우 모두 **`t` 가 없는 종점의 진행 불가 방향**에서만 도달한다. 호출부
  (`departure_time_calculator.dart`)가 구간 출발역을 넘기므로 앱에서는 사실상
  발생하지 않는다. 이 보정의 값어치는 지금 데이터 교정이 아니라, `t` 없는
  **중간역**이 생겼을 때의 방어선이다.

## 핵심 함수

- `findNextDeparture()` — `lib/domain/usecases/find_next_departure.dart`: 역별 시간표(이진탐색) 또는 배차간격으로 다음 출발 시각 계산 (`isDown`, `stationId`, `express` 파라미터). `express=true`면 급행 시간표(`tE`/`expressStationDepartures`)만 조회.
- `computeDepartureTime()` — `lib/features/route_search/utils/departure_time_calculator.dart`: 실시간 + 시간표 통합 계산 (방향 자동 결정, `stationId` 전달)
- `computeSegmentDepartures()` — 환승역에서도 방향별 시간표 기반 출발시각 계산 (`stationId` 전달)
- `isDownDirection()` — `lib/features/route_search/utils/direction_resolver.dart`: RouteSegment에서 하행/외선 여부 결정

## 데이터소스

- `TimetableDataSource` (`lib/data/local/timetable_data_source.dart`): 컴팩트 JSON 파싱 (레거시 포맷 호환, `t` 키 역별 시간표 파싱)
- `timetableProviders` (`lib/features/route_search/presentation/providers/timetable_providers.dart`): Riverpod 프로바이더
