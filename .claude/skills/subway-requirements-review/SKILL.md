# Subway Requirements Review

사용자 요청 대비 구현 완전성 검증 가이드. CLAUDE.md의 작업 워크플로우에서 요구사항 리뷰 단계에 해당.

## 검증 프레임워크

### 1단계: 요구사항 추출

사용자의 원래 요청에서 다음을 추출한다:

- **명시적 요구사항**: 직접 언급된 기능/변경
- **암묵적 요구사항**: 맥락에서 유추되는 기대 (예: "버튼 추가" → 클릭 동작도 필요)
- **비기능 요구사항**: 성능, 접근성, 호환성 등

### 2단계: 구현 매핑

각 요구사항에 대해 구현 상태를 확인한다:
- ✅ 구현됨 — 요구사항을 만족
- ⚠ 부분 구현 — 핵심은 있으나 세부사항 누락
- ❌ 누락 — 구현되지 않음
- ➕ 추가됨 — 요청하지 않은 기능이 추가됨 (오버 엔지니어링 후보)

### 3단계: 의도 부합성

구현이 사용자의 의도와 맞는지 검증:
- 기능이 사용자가 기대하는 방식으로 동작하는가
- UI 변경이 사용자가 원하는 위치/형태인가
- 데이터 흐름이 자연스러운가

### 4단계: 엣지 케이스

부산 지하철 앱 특수 엣지 케이스:
- 2호선 순환선 처리
- 4호선 진접선 분기
- 환승역 (여러 노선 교차)
- 오프라인 상태
- API 응답 지연/실패
- 역 이름 중복 (동일 역명, 다른 노선)

### 5단계: 오버 엔지니어링 감지

- 요청하지 않은 기능 추가
- 불필요한 추상화 계층
- 현재 불필요한 미래 대비 코드
- 과도한 설정 옵션
- 사용되지 않는 파라미터

### 6단계: 버그 수정 회귀 검증 (버그 수정 작업 한정)

요청이 "버그 수정 / 오류 해결 / X가 동작하지 않음" 유형이면 **기존 기능을 변경하지 않은 채로 버그만 수정했는지** 반드시 확인한다. 버그 수정 명목으로 무관한 동작이 바뀌면 새 버그를 만든다.

**판별 기준:**
- 변경된 함수/메서드의 **버그가 아닌 분기**(다른 입력, 다른 노선, 다른 상태)의 동작이 바뀌었는가?
- 기존 단위/통합 테스트가 깨졌는가? 깨졌다면 (a) 기존 테스트가 잘못된 동작을 검증하고 있었음을 입증할 수 있는가, (b) 정당한 이유가 명시되었는가?
- 변경된 데이터 구조/엔티티 필드가 **호출처 전반**에서 동일한 의미로 해석되는가?
- 공용 상수·기본값·캐시 키·API 응답 포맷 변경이 **다른 화면/노선/케이스**에 부수효과를 일으키는가?
- 변경 범위가 사용자가 보고한 시나리오를 넘어 **불필요하게 확대**되었는가?

**부산 지하철 앱 회귀 위험 영역:**
- 노선별 분기 로직 (2호선 순환, 4호선 진접선, 8호선 별내선 등) — 한 노선 수정이 다른 노선을 망가뜨리는 패턴 빈발
- 도착정보 DTO 파싱 (barvlDt/arvlCd/arvlMsg2 해석 변경) — 정상 응답 노선까지 영향
- 공용 유틸 (path_on_line, direction_resolver, estimate_arrival_seconds, dwell_time) — 사용처가 많아 부수효과 큼
- 캐시 키/구조 변경 — 기존 SharedPreferences 데이터와의 호환성
- Riverpod 프로바이더 시그니처 변경 — watch 중인 위젯들에 일괄 영향

**대조군 시나리오 매트릭스:**
버그 수정 검증 시 **사용자가 보고한 시나리오 외에** 최소 다음 케이스를 검증한다.

| 영역 | 대조군 |
|------|--------|
| 특정 노선 버그 | 다른 노선 1~2개(2호선 순환 + 비순환 노선)의 동일 기능 |
| API 응답 처리 | 정상값 / 0 / null / 누락 필드 각각 |
| 방향 결정 | 상행 / 하행 / 순환 경계 / 확장선 |
| 도착시간 계산 | 시간 직접 응답 / "N분 N초" 메시지 / "N번째 전역" 메시지 / 모두 부재 |
| UI 인터랙션 | 출발만 / 도착만 / 양쪽 선택 상태 |

검증은 (1) 호출처 grep으로 영향 범위 매핑, (2) 변경 후 `flutter test` 전체 통과 확인, (3) 대조군 시나리오에 대한 단위 테스트 추가 여부 확인으로 수행한다.

## 출력 형식

```markdown
## 요구사항 리뷰 결과

### 원래 요청
> (사용자의 원래 요청 인용)

### 기능 완전성
- ✅ [구현됨] 기능 설명
- ❌ [누락] 기능 설명 — 필요한 이유
- ⚠ [부분] 기능 설명 — 누락된 세부사항

### 의도 부합성
- ✅ 적절히 구현됨
- ⚠ 약간 다르게 구현됨: 차이점 설명

### 엣지 케이스
- ⚠ [시나리오] 미처리 케이스 설명

### 오버 엔지니어링
- ➕ [파일:줄] 불필요한 추가 설명

### 회귀 검증 (버그 수정 시 필수)
- ✅ [영역] 대조군 시나리오 정상 동작 확인
- ⚠ [파일:줄] 버그가 아닌 분기의 동작 변경 가능성: 설명
- ❌ [파일:줄] 무관한 동작이 함께 바뀜: 설명 + 복구 방향
- 영향 범위(grep으로 확인한 호출처): 파일 목록
- `flutter test` 결과: 통과 N개 / 실패 M개 (실패가 본 수정과 인과관계 있는지 명시)

### 종합 판정
- **충족률**: X/Y (N%)
- **판정**: 통과 / 수정 필요
- **권장 수정**: 우선순위별 목록
```

## subway-code-review와의 관계

이 두 리뷰는 항상 **병렬**로 실행된다:
- **subway-code-review**: "코드가 잘 작성되었는가" (품질, 보안, 성능)
- **subway-requirements-review**: "요청한 것이 만들어졌는가" (완전성, 의도)

두 리뷰의 결과를 합쳐서 수정 작업을 결정한다.
