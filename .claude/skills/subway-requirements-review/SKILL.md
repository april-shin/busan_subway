# Subway Requirements Review

사용자 요청 대비 구현 완전성 검증 가이드. CLAUDE.md의 작업 워크플로우에서 요구사항 리뷰 단계에 해당.

## 검증 프레임워크

### 1단계: 요구사항 추출

사용자의 원래 요청에서 다음을 추출한다:

- **명시적 요구사항**: 직접 언급된 기능/변경
- **암묵적 요구사항**: 맥락에서 유추되는 기대 (예: "버튼 추가" → 클릭 동작도 필요)
- **비기능 요구사항**: 성능, 접근성, 호환성 등

### 2단계: 구현 매핑

각 요구사항에 대해 구현 상태를 확인한다:
- ✅ 구현됨 — 요구사항을 만족
- ⚠ 부분 구현 — 핵심은 있으나 세부사항 누락
- ❌ 누락 — 구현되지 않음
- ➕ 추가됨 — 요청하지 않은 기능이 추가됨 (오버 엔지니어링 후보)

### 3단계: 의도 부합성

구현이 사용자의 의도와 맞는지 검증:
- 기능이 사용자가 기대하는 방식으로 동작하는가
- UI 변경이 사용자가 원하는 위치/형태인가
- 데이터 흐름이 자연스러운가

### 4단계: 엣지 케이스

서울 지하철 앱 특수 엣지 케이스:
- 2호선 순환선 처리
- 4호선 진접선 분기
- 환승역 (여러 노선 교차)
- 오프라인 상태
- API 응답 지연/실패
- 역 이름 중복 (동일 역명, 다른 노선)

### 5단계: 오버 엔지니어링 감지

- 요청하지 않은 기능 추가
- 불필요한 추상화 계층
- 현재 불필요한 미래 대비 코드
- 과도한 설정 옵션
- 사용되지 않는 파라미터

## 출력 형식

```markdown
## 요구사항 리뷰 결과

### 원래 요청
> (사용자의 원래 요청 인용)

### 기능 완전성
- ✅ [구현됨] 기능 설명
- ❌ [누락] 기능 설명 — 필요한 이유
- ⚠ [부분] 기능 설명 — 누락된 세부사항

### 의도 부합성
- ✅ 적절히 구현됨
- ⚠ 약간 다르게 구현됨: 차이점 설명

### 엣지 케이스
- ⚠ [시나리오] 미처리 케이스 설명

### 오버 엔지니어링
- ➕ [파일:줄] 불필요한 추가 설명

### 종합 판정
- **충족률**: X/Y (N%)
- **판정**: 통과 / 수정 필요
- **권장 수정**: 우선순위별 목록
```

## subway-code-review와의 관계

이 두 리뷰는 항상 **병렬**로 실행된다:
- **subway-code-review**: "코드가 잘 작성되었는가" (품질, 보안, 성능)
- **subway-requirements-review**: "요청한 것이 만들어졌는가" (완전성, 의도)

두 리뷰의 결과를 합쳐서 수정 작업을 결정한다.
